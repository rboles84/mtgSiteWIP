## What the branch supports today

Right now, the generated Archscry stack is built around **20 active expressions**: five mono colors, ten Ravnica guild pairs keyed by color code, and five Strixhaven colleges keyed by faction name. You can see that in `data/factions.json` and `data/placement-model.json`, where the placement model’s `active_expression_keys` are a mixed set such as `WU`, `WR`, `BG`, `LOREHOLD`, `PRISMARI`, `SILVERQUILL`, and the five mono colors. In other words, the product already supports both abstract color identities and world-skinned duplicates for the same colors, but only for mono and two-color space. fileciteturn17file0L3-L3 fileciteturn18file0L3-L3

The preview homepage is even narrower. `assets/js/newindex2.js` hard-codes a local `identities` array that starts with the five mono colors, then adds the ten guilds and five Strixhaven colleges. It also hard-codes a `heroManaLoreKeys` lookup for exactly those identities, and the display-kind helper in that file only returns `Color`, `College`, or `Guild`. There are no shard, wedge, New Capenna family, four-color, or five-color identities defined there today. fileciteturn31file0L3-L3 fileciteturn32file0L3-L3

## What adding all of these actually means

If you deduplicate by color identity, your request is smaller than the raw list of names makes it look. The three-color part resolves to **10 unique identities**: five shards and five wedges. The extra New Capenna names are alternate labels for the shard color sets, not new color combinations. The four-color part resolves to **5 unique identities**, each with two naming conventions in common circulation: Yore/Artifice, Glint/Chaos, Dune/Aggression, Ink/Altruism, and Witch/Growth. Then there is the single five-color identity commonly referred to as **WUBRG**. So the canonical implementation target is **16 new color identities** if you want full three-color, four-color, and five-color coverage at the color-identity level. citeturn13view1turn13view2turn14view0turn13view4turn15view0

The catch is that Vox Mana does **not** currently model identities as pure color combinations. It models them as named, worlded, typed expressions with `name`, `world`, `institution_type`, `layered_identity`, and dossier copy. That is why `WB` and `SILVERQUILL` can coexist as active expressions even though they share the same underlying colors. So before you add Bant and Brokers, you need to decide whether they are merely aliases for one canonical three-color identity, or whether they should be distinct Vox Mana presentations the same way Orzhov and Silverquill are distinct today. That decision changes the scope dramatically. fileciteturn27file0L3-L3 fileciteturn18file0L3-L3

In practice, that gives you two scope options. A **names-and-browse** implementation means 16 canonical color identities plus alias tables. A **full Vox Mana dossier** implementation means something closer to 21 new presentational entries if you want separate world skins for shards, New Capenna families, wedges, the five four-color identities, and WUBRG—because the current product architecture already treats same-color worlds as different expressions when it has authored voice and world context for them. fileciteturn27file0L3-L3 fileciteturn18file0L3-L3

## Where the code will break first

The single biggest technical blocker is that the repo does **not** yet separate internal identity keys from display order or display names. The shared identity utilities and Scryfall index builder sort colors in WUBRG order through `sortColorCodes` and `colorIdentityKey`. But the preview home uses user-facing codes like `GW`, `RW`, and `GU` for Selesnya, Boros, and Simic, while the generated artifacts use `WG`, `WR`, and `UG`. That mismatch is already survivable for pairs because `commander-dossier.js` carries alias maps, but it becomes a real maintenance hazard once you add three-color identities, alternate family names, and four-color naming conventions. fileciteturn26file0L3-L3 fileciteturn34file0L3-L3 fileciteturn31file0L3-L3 fileciteturn17file0L3-L3 fileciteturn24file0L3-L3

The data pipeline is also intentionally narrow today. `data/identity-layers.schema.json` hard-requires only the current mono, guild, and college expression set. `research/build-faction-artifacts.mjs` has a fixed `RAW_TO_KEY` map for the existing 15 non-mono authored factions. `data/placement-model.json` declares only 20 active expressions. And `assets/js/quick-reading-tests.js` still asserts that `institution_type` must match `guild|college|color`. In other words, the current schema, generator, model, and test suite will all reject shard, wedge, family, four-color, and five-color additions until you intentionally widen the contract. fileciteturn38file0L3-L3 fileciteturn19file0L3-L3 fileciteturn18file0L3-L3 fileciteturn37file0L3-L3

On the presentation side, the code is duplicated in a way that will make brute-force additions expensive. `newindex2.js` maintains its own hand-authored identity catalog, its own lore-key mapping back into `data/factions.json`, and its own identity-kind logic. `commander-dossier.js` maintains separate routing alias maps and color-identity slugs for mono and two-color identities, while the project architecture notes that Strixhaven colleges are intentionally collapsed to guild/color analogs for external deck directories. That means adding shards, wedges, New Capenna families, and four-color names by hand would create even more duplication unless you first centralize the identity registry. fileciteturn31file0L3-L3 fileciteturn32file0L3-L3 fileciteturn24file0L3-L3 fileciteturn12file0L3-L3

There is also one very specific visual gotcha in the preview home: the chart/radar layer is **almost** generic, because it already loops over `identity.components` and can draw more than one source profile, but the glow blending logic only defines three positional gradient anchors before falling back to a center default. Three-color previews are therefore plausible with minor tuning, while four-color previews will visually stack multiple colors into the same center glow unless you rewrite that gradient placement logic. fileciteturn32file0L3-L3

## What the implementation should look like

The right first move is to create or expand a **canonical multicolor identity registry** in the hand-authored layer, not to start dropping more objects into `newindex2.js`. That registry should carry, at minimum, an internal key, a canonical color array, a separate display-order array for mana symbols, a primary display name, alternate names, kind, world/presentation metadata, and routing aliases. The repo already has the beginnings of this shape in `data/identity-layers.json`, and the architecture docs explicitly treat it as the canonical source for identity data while treating `data/factions.json` and `data/placement-model.json` as generated outputs. fileciteturn15file0L3-L3 fileciteturn12file0L3-L3 fileciteturn27file0L3-L3

Once that registry exists, the minimum file list for a maintainable expansion is straightforward. You would need to widen `data/identity-layers.json` and `data/identity-layers.schema.json`; refactor `research/build-faction-artifacts.mjs` so it is registry-driven rather than a fixed `RAW_TO_KEY` lookup; extend `assets/js/identity-layers.js` so `getExpressionKindLabel()` understands kinds like `shard`, `wedge`, `family`, `four-color`, and probably `five-color`; update `assets/js/commander-dossier.js` to understand new routing aliases and slugs; update `research/scryfall-dictionary.js` to add missing alternate names; and replace the preview home’s hard-coded identity list in `assets/js/newindex2.js` with generated or registry-fed data. If you want only browse/search/home-preview support, you can stop there. If you want full Archscry dossier support, you then need to author the raw expression data and regenerate `data/factions.json`, `data/placement-model.json`, and any server-side context artifacts. fileciteturn38file0L3-L3 fileciteturn19file0L3-L3 fileciteturn26file0L3-L3 fileciteturn24file0L3-L3 fileciteturn35file0L3-L3 fileciteturn31file0L3-L3 fileciteturn32file0L3-L3

The most important product decision inside that implementation is whether New Capenna families are aliases or separate authored skins. If you follow the current Azorius/Silverquill pattern, they should probably be separate presentations that share a canonical color identity underneath. If you want the smaller build, then Bant/Brokers and the four-color nickname pairs should be alternate labels that resolve to the same underlying record. Given the current architecture, my recommendation would be: **canonical color-identity records first, optional world skins second**. That preserves the current lore-oriented product style without forcing you to duplicate everything immediately. fileciteturn27file0L3-L3 fileciteturn18file0L3-L3 citeturn13view1turn13view2turn14view0turn13view4turn15view0

## Effort and the most sensible path

If the goal is **display, search, and browse support only**, this is not a massive project. The preview chart layer already understands multi-component identities in principle, the parser already knows most canonical shard/wedge/four-color names, and the biggest work is centralizing the registry, adding missing aliases, extending labels, and eliminating the preview home’s hard-coded identity duplication. Based on the current code shape, that looks like roughly **one to two focused days** of implementation and light regression work. That estimate is an inference from the fact that the visual layer is partly generic already, while the real pain is naming and data duplication. fileciteturn32file0L3-L3 fileciteturn35file0L3-L3 fileciteturn26file0L3-L3

If the goal is **full dossier support without expanding the adaptive placement engine**, the cost jumps meaningfully. At that point you are authoring real identity copy, archetypes, routing, deck links, and presentation metadata for 10 three-color identities, 5 four-color identities, and probably WUBRG, while deciding whether New Capenna should be alias-only or full alternate skins. On the current architecture, that is closer to **about a workweek** if you keep Capenna as aliases, and somewhat more if you give Bant and Brokers separate authored surfaces. That estimate comes from the repo’s current pattern of rich faction entries and generated artifacts, not just the number of names. fileciteturn17file0L3-L3 fileciteturn27file0L3-L3 fileciteturn12file0L3-L3

If the goal is **true Archscry placement support**—meaning the adaptive questionnaire can actually place a user into these new identities—the scope is no longer a simple UI story. The current model, tests, and generated outputs are tightly tuned around 20 expressions, and Wizards’ own Commander 2016 design retrospective frames four-color identity design as unusually difficult and one of the hardest Commander design problems they had tackled. In Vox Mana terms, that means new priors, new evidence terms, new lateral-inhibition relationships, new raw authored data, and a serious tuning pass so the model does not become noisy or mushy. I would treat that as a **multi-week content-and-model project**, with **two to three weeks** being the realistic range for a solid first version. That estimate is an inference, but it is strongly supported by both the current repo’s narrow model and Wizards’ own explanation of how hard four-color identities are to make feel distinct. fileciteturn18file0L3-L3 fileciteturn37file0L3-L3 citeturn15view0

The bottom line is simple: the cheapest sane path is **not** “add more entries to `newindex2.js`.” It is “define one canonical multicolor identity registry, separate internal keying from display order and aliasing, then let preview, dossier, search, and routing all read from that.” If you take that path, three-color support is very manageable, four-color support is still reasonable, and WUBRG becomes a straightforward extension.
